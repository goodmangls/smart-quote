🐛 RouteSection 비결정 실패의 근본 원인 제거 — `getAllByRole('option')` → 범위 좁힌 DOM 질의 (최악 913ms → 107ms) — **순서 의존이라는 첫 가설은 틀렸다.** `unserviceable[0]` 을 의심했지만 오류 전문을 잡으니 단언 실패가 아니라 `Test timed out in 5000ms` 였다 — 추측 전에 오류를 읽은 게 갈림길이었다. 계측 결과 헬퍼의 `screen.getAllByRole('option')` 이 범인이다: **같은 206개 요소를 같은 개수로 반환하면서 400ms~2621ms 로 6배 요동**하고(`querySelectorAll` 은 0.4~1.0ms 로 일정), 문서의 모든 요소에 ARIA role 계산과 접근성 가시성 검사를 돌리기 때문이다. 실패 테스트는 캐리어 3종을 돌며 이걸 3번 호출해 최악 7.8초 — 5초 기본 타임아웃을 넘는다. 단독 실행은 부하가 없어 통과하고 CI 는 워커 구성이 달라 통과했다. ⚠️**타임아웃을 늘리지 않았다** — 그건 증상 처치고, 200개짜리 목록에 초 단위 역할 질의를 도는 것 자체가 문제다. 헬퍼를 destination select 로 **범위를 좁히고** DOM 질의로 바꿨다: 최악 테스트 913ms → **107ms**, 파일 전체 2.24s → **336ms**, 타임아웃 여유 5.5배 → **47배**. ⚠️라벨이 select 에 `htmlFor`/`id` 로 연결돼 있지 않아 `getByLabelText` 를 쓸 수 없어 위치로 잡되, **옵션 개수 가드**(<100 이면 throw)를 뒀다 — 마크업 순서가 바뀌면 조용히 엉뚱한 select 를 검사하는 대신 큰 소리로 실패한다. 🔴**빨라진 테스트가 결함을 못 잡으면 느린 것보다 나쁘므로 결함 주입으로 판별력을 증명했다**: 미취급 라벨 제거 → 그 라벨을 검사하는 **정확히 2건** RED, 모든 접미사 공백화 → **3건** RED, 가드 임계값을 실제 개수보다 높게 올림 → `expected the destination select first, found 192` 로 발동. 컴포넌트는 매 주입 후 복원했고 무변경이다. 검증: tsc 0, eslint 0, **전체 스위트 6회 연속 1797/1797** — 수정 전에는 같은 6회 시도의 **1회차에서 바로 재현**됐다(그 직전 조사에서는 4회 중 2회 실패). 타이밍 결함이라 결정적 단위 테스트로는 못 잡으므로 반복 실행이 검증 수단이고, 그래서 성능 단언을 테스트로 남기지 않았다(그 자체가 새 플레이크가 된다). ⚠️부수 발견 — **라벨이 select 에 연결돼 있지 않은 것은 실제 접근성 결함**이다. 이번 범위 밖이라 손대지 않고 테스트 주석에 위치 기반 선택의 근거로 남겼다. ⚠️`RateTableViewer.test.tsx` 에도 `getByRole('option')` 이 하나 있으나 대상 select 가 작아 같은 증상이 없다 — 큰 목록에 역할 질의를 쓸 때만 문제다.
